## Features
- [x] `qemu_mouse` tool — QMP `input-send-event` absolute pointer move + click (guests with mouse support become fully drivable) — added `src/qemu_mcp/mouse.py` (`move_events`/`click_events`, pure functions building the QMP event list from x/y fractions of screen width/height in 0.0-1.0, scaled to QEMU's fixed 0..32767 absolute-pointer axis range) and a `qemu_mouse(name, x, y, button=None)` tool in `server.py` that calls `input-send-event` with those events. Documented in the README tools table. Verified: `ruff check`, `python -m compileall src`, and all 182 tests pass (7 new `tests/test_mouse.py` cases covering axis scaling/clamping and button validation, plus the stdio handshake now asserting `qemu_mouse` is in the registered tool list). Not verified: an actual guest cursor moving/clicking under real QEMU (needs a GUI guest with an absolute pointer device and a local boot test — no QEMU in this environment).
- [x] Bidirectional serial: switch `-serial file:` to a chardev socket so a new `qemu_serial_send` tool can write to the guest console; keep the file log — added `src/qemu_mcp/serial.py` (`chardev_args`: builds `-chardev socket,...,logfile=...,logappend=on` + `-serial chardev:serial0` instead of the old write-only `-serial file:`, so the plain-text log qemu_serial/qemu_wait_serial read from is unchanged, but a TCP socket on 127.0.0.1 now also carries the same COM1 traffic bidirectionally; `SerialConsole`: connects to that socket lazily and holds the connection open for the VM's lifetime rather than reconnecting per send, since QEMU treats a client disconnect on a socket chardev as a hangup on the serial line, which can kill a guest login shell). `vm.boot()` now allocates a second free port for the chardev and wires `VM.serial_console`; `vm.stop()` closes it. Added `qemu_serial_send(name, text)` in `server.py`. Documented in the README tools table, feature bullet list, and the kernel-test example (rewritten to use it for a serial-only guest shell). Verified: `ruff check`, `mypy --strict src`, `python -m compileall src`, and all 213 tests pass (5 new `tests/test_serial.py` cases: chardev arg-building, connect-once-and-write and connection-reuse against a real local TCP socket, and reconnect-after-`OSError` via a monkeypatched fake socket to keep it deterministic instead of racing real TCP teardown timing; stdio handshake now asserts `qemu_serial_send` is registered); added `tests/test_serial.py` to the CI test list. Not verified: an actual write reaching a real guest's serial console and being echoed back (needs a local boot test against a guest with a serial shell — no QEMU in this environment). Follow-up: if a guest's getty *does* hang up when the very first client connects to the chardev socket (some getty configs watch DCD), we'd want a config knob to disable that - untested without real QEMU.
- [x] Snapshot tools — `qemu_snapshot_save` / `qemu_snapshot_load` — added `src/qemu_mcp/snapshot.py` (`validate_tag`, `save_command_line`/`load_command_line`: builds `savevm <tag>`/`loadvm <tag>` HMP command lines, restricting `tag` to `[A-Za-z0-9_.-]+` since it's tokenized into that command-line string with no escaping) and `qemu_snapshot_save(name, tag)` / `qemu_snapshot_load(name, tag)` tools in `server.py` that send it via QMP `human-monitor-command` (QEMU has no native QMP savevm/loadvm, only the HMP monitor commands). While wiring this up found that `qemu_boot`'s `disk` param was hardcoded to `-drive ...,format=raw` regardless of the actual file - so passing a real qcow2 disk got silently forced into raw mode, and the snapshot tools would have failed on every qcow2 image passed through `qemu_boot`. Fixed by adding `vm.disk_format()` (reads the qcow2 magic bytes, defaults to raw) and using it instead of the hardcoded format. Documented in the README tools table and `qemu_boot`'s docstring (qcow2 required for snapshots, auto-detected). Verified: `ruff check`, `python -m compileall src`, and all 202 tests pass (7 new `tests/test_snapshot.py` cases for tag validation/command-line building, 3 new `tests/test_vm.py` cases for `disk_format`, stdio handshake asserting both new tools are registered); added `tests/test_snapshot.py` to the CI test list. Not verified: an actual `savevm`/`loadvm` round-trip against a real qcow2 disk under real QEMU (needs a local boot test — no QEMU in this environment).
- [x] `machine` parameter on `qemu_boot` (aarch64/riscv64 need `-M virt`; document per-arch examples in README) — added `machine: str | None = None` to `qemu_boot` and `vm.boot`, passed through as QEMU's `-M <machine>` when set; boot confirmation message now shows it. Documented in the tools table and a new "Non-x86 archs" README section with aarch64/riscv64 examples pointing at `machine="virt"`. Verified: `ruff check`, `python -m compileall src`, and all 175 existing tests (`test_keys.py`, `test_vm.py`, `test_stdio_handshake.py`) pass unchanged since none of them call `vm.boot()` directly. Not verified: an actual `-M virt` boot on real aarch64/riscv64 QEMU — needs a local boot test, no QEMU in this environment.
- [x] `qemu_wait_screen` — poll screendumps until the framebuffer stops changing (boot-settled detection for VGA-only guests) — added `src/qemu_mcp/screen.py` (`hash_file`: SHA-256 of a screendump PPM, since an unchanged framebuffer produces a byte-identical file; `StabilityTracker`: pure state machine counting consecutive identical hashes) and a `qemu_wait_screen(name, timeout_s=30, poll_interval_s=1.0, stable_polls=3)` tool in `server.py` that polls `screendump` in a loop and feeds each hash to the tracker, returning SETTLED/VM EXITED/TIMEOUT. Documented in the README tools table. Verified: `ruff check`, `python -m compileall src`, and all 208 tests pass (6 new `tests/test_screen.py` cases for `hash_file`/`StabilityTracker`, stdio handshake asserting `qemu_wait_screen` is registered — ran in a clean venv since this container's system `mcp` package collides with the real PyPI `mcp` SDK); added `tests/test_screen.py` to the CI test list. Not verified: an actual settle-detection run against a real QEMU display transitioning from a boot splash to a stable screen (needs a local boot test — no QEMU in this environment).

## Quality
- [x] Pin `mcp` below the breaking 2.0.0 release — unpinned `mcp>=1.2.0` had started resolving to `mcp==2.0.0`, which moved `FastMCP`/`Image` from `mcp.server.fastmcp` (removed) to `mcp.server.mcpserver` as a renamed `MCPServer` class with a different API. That broke `from mcp.server.fastmcp import FastMCP, Image` in `server.py` outright — a fresh `pip install qemu-mcp` today fails at import time, and the very CI pipeline turned green yesterday would go red on its next run. Fixed by pinning `mcp>=1.2.0,<2.0.0` in `pyproject.toml`, same shape as the existing ruff pin. Verified in two fresh venvs: unpinned resolves to `mcp==2.0.0` and reproduces `ModuleNotFoundError: No module named 'mcp.server.fastmcp'` (confirmed against unmodified `origin/main` too, so this isn't new); pinned resolves to `mcp==1.29.0` and `ruff check`, `python -m compileall src`, and all 175 tests (`test_keys.py`, `test_vm.py`, `test_stdio_handshake.py` — including the real stdio handshake, which needs no QEMU) pass. Follow-up: eventually migrate to the mcp 2.0 `MCPServer` API deliberately rather than staying pinned to 1.x forever.
- [x] Unit tests for `keys.py` (`char_to_keys` full printable-ASCII round-trip, `parse_combo` good + error cases) — no QEMU needed, plain pytest (`tests/test_keys.py`, 168 cases; `pytest>=7` added as the `test` extra)
- [x] GitHub Actions CI: ruff + the pytest unit tests + `mcp_handshake`-style stdio smoke on ubuntu-latest and windows-latest (handshake needs no QEMU) — `.github/workflows/ci.yml` runs `ruff check` plus `tests/test_keys.py`, `tests/test_vm.py`, and the new `tests/test_stdio_handshake.py` (spawns the real server over stdio, initializes an MCP `ClientSession`, asserts the expected tool names come back) on ubuntu-latest and windows-latest with Python 3.12. Took 3 pushes to actually go green on GitHub: (1) `pip install ruff` floated to 0.16.0, whose wider default ruleset broke both OSes - fixed by pinning `ruff==0.16.0` and adding an explicit `[tool.ruff.lint] select` in `pyproject.toml` so this can't silently drift again; (2) that surfaced a real, pre-existing Windows bug in `tests/test_vm.py`'s `_make_fake_binary` - `shutil.which()` only recognizes `PATHEXT`-suffixed files on Windows, so the extension-less fake binary was invisible to `find_qemu`'s exact-match path even though `_installed_arches`' directory scan found it fine. Fixed by giving the helper a `.exe` suffix on `win32`, matching a real QEMU install; (3) that in turn exposed `shutil.which()` returning the `PATHEXT` suffix in a different case (`.EXE`) than the file we created (`.exe`) - same file on Windows' case-insensitive filesystem, but a strict string `==` failed. Fixed by comparing with `os.path.normcase()`. Run 30274784806 (a4a453c): both `test (ubuntu-latest)` and `test (windows-latest)` jobs green, confirmed via the Actions API - CI is genuinely working, not just locally green.
- [x] Type-check pass (`mypy --strict src/`) and fix what it finds — 13 errors across 4 files, all fixed: missing `dict`/`Popen` generic type args (`mouse.py`, `qmp.py`, `server.py`, `vm.py`), a `no-any-return` on `_free_port`'s `getsockname()[1]` (annotated the intermediate variable), and a real latent bug in `qmp.py` — `QMPClient.sock` is typed `socket.socket | None` and `close()` sets it back to `None`, but `_read_msg`/`command` used it unchecked, so calling either after `close()` would raise a confusing `AttributeError` instead of a clear error; added explicit `if self.sock is None: raise QMPError(...)` guards. Added `mypy --strict src` as a CI step (pinned `mypy==2.3.0` alongside the existing `ruff==0.16.0` pin, same drift-avoidance rationale) so this can't silently regress.
